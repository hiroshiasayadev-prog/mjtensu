# MLDB-ADR-ORCHESTRATION-005: Define Worker API semantics

## Context

MLDB v1 uses a pull-oriented Worker boundary. Workers execute one Training or Evaluation attempt at a time while Controller owns Queue state, Run allocation, canonical result acceptance, and Study progression.

A distributed Worker must tolerate temporary Controller outages and network failures without turning them into false Training or Evaluation failures. Conversely, an actual `train()` or `evaluate()` failure must not cause the Worker to rerun the same domain execution indefinitely on its own.

The API also needs retry-safe semantics because a request may reach Controller and commit state even when the response is lost. In particular, work acquisition and result reporting must tolerate ambiguous communication outcomes without creating duplicate Runs or duplicate canonical results.

## Decision

Define five logical Worker API operations:

```text
acquire work
heartbeat
retrieve immutable asset
upload candidate artifact
report attempt outcome
```

Exact HTTP paths, authentication, content streaming, and serialization details remain separate wire-contract decisions.

### Failure classes

Worker behavior distinguishes three classes of failure.

| class | examples | Worker behavior |
|---|---|---|
| communication failure | Controller unreachable, connection timeout/reset, response lost, transient Controller service failure | Preserve current Worker state and retry the same logical operation every 10 seconds without a retry-count limit. |
| definitive Controller response | no work, stale lease, cancellation request, rejected candidate, unsupported request | Do not retry the same operation as a communication retry; follow the returned control decision. |
| domain execution failure | `train()` or `evaluate()` raises/fails, execution-local result preparation fails | Do not rerun the same domain invocation locally. Report the attempt as failed; Controller/Queue decides whether a new attempt is scheduled. |

A communication failure is not a Training Run or Evaluation Run failure by itself.

A Worker may stop communication retry when the Worker process is intentionally shut down.

Protocol incompatibility such as an unsupported Worker API version is not treated as an endlessly retryable communication failure. It is a fatal compatibility error requiring configuration or software correction.

### Communication retry

For a retryable communication failure, Worker waits 10 seconds and retries the same logical operation.

V1 uses no exponential backoff and no finite retry limit for this class.

The retry must preserve operation identity where ambiguity could otherwise duplicate state.

Communication retry applies independently to work acquisition, heartbeat, asset retrieval, candidate upload, and attempt-outcome reporting.

A valid Controller response ends communication retry for that request even when the response reports `no_work`, cancellation, stale lease, or another non-success control outcome.

### Acquire semantics

Worker initiates work acquisition and declares its Worker identity plus the execution kinds it can accept.

One Worker process handles at most one active attempt at a time.

An acquire request carries an opaque acquisition request token generated by Worker and reused unchanged when that acquire operation is retried after communication failure.

Controller must make acquisition retry-safe. If the first acquire committed an attempt but its response was lost, retrying the same acquisition token must return the same still-authorized assignment rather than allocate another child Run.

A successful assignment contains one concrete Run identity, one lease token, and all resolved execution input identities needed for one Training or Evaluation attempt.

`no_work` is a valid response rather than a communication failure.

### Assignment semantics

Worker receives resolved execution intent from Controller and does not infer Study progression from repository contents.

A Training assignment identifies at least:

- concrete Training Run ID;
- lease identity and expiry information;
- Task;
- Corpus;
- Architecture;
- Train Protocol;
- validated training seed;
- complete resolved public parameter mapping;
- immutable artifact descriptors required to obtain the inputs.

An Evaluation assignment identifies at least:

- concrete Evaluation Run ID;
- lease identity and expiry information;
- Task;
- Corpus;
- Model;
- Evaluation Protocol;
- complete resolved public parameter mapping;
- immutable artifact descriptors required to obtain the inputs.

Study Run, trial, and stage lineage may be included for observability, but Worker does not use that lineage to decide which work should run next.

### Heartbeat semantics

Worker sends heartbeat while an attempt remains active, including while it is downloading inputs, executing domain code, preparing candidates, or waiting for Controller to accept a completed result.

Heartbeat authenticates the current attempt through its attempt identity and lease token.

A successful heartbeat may extend the lease and may return a cancellation request.

Communication failure while sending heartbeat does not itself fail the attempt. Worker keeps the current execution state and retries heartbeat communication every 10 seconds.

A network partition may nevertheless allow Controller-side lease expiry because Controller cannot distinguish an unreachable Worker from a dead Worker indefinitely. If Controller later returns that the lease is stale or superseded, Worker must stop treating the attempt as authoritative and must not force late results into canonical state.

### Immutable asset retrieval

Worker obtains immutable Corpus bytes, executable asset implementations, canonical Model weights, or other required immutable inputs through Controller-provided descriptors.

A descriptor identifies the expected immutable object and its integrity information such as SHA-256 where the underlying asset contract provides it.

Worker may reuse a local cached object only after matching the required content identity.

Communication failure during retrieval causes retry of retrieval rather than domain execution failure.

Integrity mismatch after bytes are obtained is not a communication failure. Worker must not execute with bytes that fail the assignment integrity contract and must report the attempt failure or assignment error through the outcome channel.

### Candidate artifact upload

Worker uploads execution-local candidate artifacts before asking Controller to accept successful formal results when bytes are too large or unsuitable for the outcome message itself.

Candidate upload is scoped to one attempt and one declared candidate key.

Retrying the same candidate key with the same content identity is idempotent.

A retry that presents different bytes for an already accepted candidate identity must be rejected rather than silently overwrite the earlier candidate.

Candidate bytes remain non-canonical until Controller accepts them through the applicable Training or Evaluation result contract.

### Attempt outcome reporting

Worker reports exactly one intended domain outcome for a concrete attempt:

```text
success
failed
cancelled
```

For `success`, Worker supplies Training or Evaluation result metadata plus references to any uploaded candidate artifacts.

For `failed`, Worker supplies concise failure type/message information suitable for Controller to persist where the child Run contract permits it.

For `cancelled`, Worker reports cooperative termination after a Controller cancellation decision or another intentional local stop covered by the assignment contract.

A domain execution failure does not cause Worker to call `train()` or `evaluate()` again for the same attempt. Worker reports `failed`; any retry is a new Queue attempt with a new child Run ID selected by Controller.

If communication fails while reporting `success`, `failed`, or `cancelled`, Worker retains required local outcome/candidate state and retries the same outcome report every 10 seconds until Controller gives a definitive response or the Worker process is intentionally terminated.

### Outcome idempotency

Outcome reporting must tolerate loss of the Controller response after canonical commit.

If Controller already accepted and terminalized the same attempt, repeating the same outcome report must return the already-established final acknowledgement without creating another child Run or another canonical result.

A conflicting later outcome for an already terminalized attempt must not mutate terminal canonical history.

A stale or superseded lease may be rejected when Controller has not already accepted that same attempt outcome.

### Controller authority

Worker never decides that a logical Queue job is satisfied.

For Training, job satisfaction occurs only after Controller validates and commits canonical learned state, completes the Training Run, and ensures its Model.

For Evaluation, job satisfaction occurs only after Controller validates formal outputs and completes the Evaluation Run.

Worker success means only that Worker has produced a candidate domain result for Controller acceptance.

## Rationale

Infinite fixed-interval communication retry prevents temporary Controller/network outages from being misclassified as model-training or evaluation failures.

Keeping domain retry under Controller/Queue control preserves immutable Run-attempt history and prevents one Worker from silently rerunning failed computation under the same Run identity.

Retry-safe acquisition is necessary because Controller may commit a Run and Queue attempt before the assignment response reaches Worker.

Retry-safe outcome reporting is necessary because Controller may commit canonical results before the acknowledgement reaches Worker.

Keeping Worker ignorant of Study progression preserves the control-plane/data-plane boundary and allows the same Worker implementation to execute both training-derived and existing-Model Study work.

## Rejected alternatives

### Treat Controller communication failure as child Run failure immediately

Temporary Controller restart or network loss would create false failed Runs and unnecessary recomputation.

### Let Worker retry `train()` or `evaluate()` automatically after domain failure

That would hide multiple execution attempts behind one Run identity and bypass Queue retry policy.

### Use a finite communication retry count

A finite count converts a prolonged Controller outage into a Worker-side domain failure even though the computation itself may still be valid. V1 prefers indefinite retry until a definitive Controller decision is obtained.

### Use exponential communication backoff

The initial deployment is small and local enough that a fixed 10-second interval is simpler to reason about. This may be revised later if scale requires jitter or backoff.

### Let Worker inspect Study plans and schedule follow-up work itself

Study progression and dependency release belong to Controller/Queue. Worker should execute only the assignment it receives.

## Consequences

Worker implementation needs persistent in-process or local execution state sufficient to resend ambiguous acquire, candidate, and outcome operations after communication failure.

The Worker API wire contract must expose an acquisition request token and attempt lease identity sufficient for idempotent replay.

Queue storage must be able to associate a concrete attempt with the acquisition request that created it so an ambiguous acquire can be replayed safely.

Worker keeps heartbeat activity alive through result-acceptance completion rather than stopping heartbeat immediately when `train()` or `evaluate()` returns.

Controller must provide definitive responses for stale lease, cancellation, no-work, accepted-result replay, and incompatible requests so Worker can distinguish them from communication failure.

Exact lease duration remains separate from the fixed 10-second communication retry interval.
